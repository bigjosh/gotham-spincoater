## Combined PIO, RPM seeking, recipes and Wi-Fi — 2026-09-08

The application now uses one combined PIO machine and one DMA channel per enabled fan. Each machine generates 10 kHz PWM, samples tach at the midpoint of its longer phase, counts full tach periods, and latches LOW on STOP or command starvation. Core 1 owns the drivers and runs independent RPM seekers at a nominal 50 Hz; core 0 handles the six-card TFT, captive HTTP/DNS portal, and idle recipe storage. Only fan #0 is enabled on GP18/GP19.

- **147 host tests pass.** These cover encoded PIO timing, hardware-register/lifecycle behavior, recipes and bounded correction, startup/coasting/dropout cases, FIFO overflow versus quiet detection, core shutdown and START/edit races, HTTP/DNS, and browser-script interactions, alongside the legacy tests.
- **Current driver on the board:** synthetic 100 Hz tach produced exactly 3,000 RPM at 0%, 25%, 50%, 75%, and 100% PWM. Repeated internal high/low pulse measurements were 26/75 µs, 50/50 µs, and 76/26 µs at 25%, 50%, and 75%; these are self-clocked measurements, not external oscilloscope calibration. Sixty changing duty commands preserved valid tach data. STOP stayed LOW after release until explicit rearm. Disabling command DMA parked LOW and reported `command_underrun`. Intentional RX FIFO overflow invalidated old measurements and recovered with new periods.
- **Six-engine resource test with Wi-Fi:** six simultaneous state machines/DMA channels in PIO0/PIO2 each read 3,000 RPM with full eight-period windows and no new overflow, while an open AP remained active. All six hardware stop latches parked before Python serviced them. This used shared dummy GP0 PWM and GP1 tach, plus GP20 as a simulated STOP; it proves concurrent resource/capture operation, not six independent physical waveforms or six motors. [Transcript](capacity-board-test.txt).
- **Real fan, speed changes:** an initial 0.02 correction gain caused substantial low-speed startup overshoot. The final 0.01 gain retained the ceiling of 10 PWM percentage points/s and completed 0 → 1,200 → 2,400 → 1,600 → 3,000 → 0 RPM, including a zero-slew downward target jump. Startup still has a transient at 1,200 RPM; the measured hold eventually settles in the agreed ±50 RPM band. There were no tach FIFO overflows. [Final-gain transcript](seeker-board-test.txt).
- **Complete application with real wireless traffic:** the default 15 s up / 30 s dwell / 15 s down recipe completed. In the final run, the 3,000 RPM dwell samples were about 2,952–2,963 RPM at 97.6–97.7% requested power, inside ±50 RPM. Recipe elapsed time was 73.4 s including settling; a 20 s test setup window preceded START. Maximum observed control-loop lateness was 6 ms, with no tach FIFO overflows. The TFT updated throughout, core 0 performed explicit garbage collection, and an external Wi-Fi client repeatedly requested status and the full 15.8 KB editor through the ramp and over 20 seconds of the hold. [Transcript](app-board-test.txt).
- **Portal:** Windows joined the password-free Gotham Spinner AP using an otherwise idle Wi-Fi adapter while Ethernet retained its primary route. Actual HTTP config save/readback, full page transfer, wildcard DNS, captive-probe redirect, and HTTP 409 edit rejection during a recipe passed. The final stress client completed 54 repeated status/page requests, with observed hold readings of 2,952–2,963 RPM and no tach overflow. [Transcript](wifi-portal-test.txt). The first harness outlived the test's deliberate AP shutdown; its termination condition now finishes during the hold. A separate truncated-response failure exposed the 2-second idle timeout expiring during long display redraws. The dashboard now services the portal between drawing batches, and the idle timeout is 5 seconds; the final over-the-air retest passed.

Automated native file selection for import was unavailable; the actual import JavaScript passed its host test. The Pico has also served the same self-contained editor over its real AP.

Implementation checks on hardware caught unsupported string-form injected JMP instructions and the absence of `socket.getsockname` in this MicroPython build; both are corrected and covered by regressions. Worker heartbeat grace now starts at thread launch, after potentially slow display initialization.
